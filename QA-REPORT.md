## 5. Defects and observations

### D1 — Auto-stitch verification hook is non-deterministic (severity: minor)
- **Where:** `OpenStitch/Views/ContentView.swift:224-239` (`loadOpenedFiles`, `autoStitchIfRequested`), invoked from both `.task` (line 75) and `.onReceive` (line 69).
- **Repro:** launch with two solid-colour files and `OPENSTITCH_AUTOSTITCH=1` (command 5c). On 2 of 3 launches the app imported both screenshots but no error alert appeared (and with samples, autostitch worked 3/3). The env var was confirmed present in the running process (`ps eww`).
- **Expected:** deterministic alert (or result) after auto-stitch.
- **Actual:** sometimes only the main window; the import happened but stitching never ran.
- **Likely cause:** both call sites check `workspace.screenshots.count >= 2` immediately after their own `loadOpenedFiles()`; when the open-file events arrive in separate waves or the `Group` identity flips from empty to list state (cancelling/restarting `.task`), no invocation observes both screenshots after both imports finish. This is a DEBUG-only automation hook; the user-facing ⌘↩ / Stitch button path is unaffected.
- **Evidence:** `Verification/overlap-failure-retry.png` (2 imported screenshots, no alert) vs `Verification/overlap-error-alert.png` (alert shown).
- **Suggested fix (for the author):** make `loadOpenedFiles`/import drive auto-stitch from a single `onChange(of: screenshots.count)`-style trigger, or await the import before checking the count and remove the duplicated trigger.

### D2 — `ImageLoader.isSupportedImage` trusts the filename extension (severity: nit)
- **Where:** `OpenStitch/Stitching/ImageLoader.swift:26-30`.
- **Actual:** any URL whose extension maps to `public.image` is "supported" even if it is a directory or a corrupt file (`fake.png`). Downstream `metadata`/`loadImage` return nil and `StitchWorkspace.add` reports "The selected files could not be opened as images.", so there is **no crash** and no silent corruption — only a slightly misleading pre-check and a wasted decode attempt.
- **Evidence:** `testUnsupportedFilesAreRejected` asserts the graceful downstream behavior.

### D3 — Matching heuristic can accept structurally correlated "unrelated" images (severity: nit; inherited from iOS spec)
- **Where:** `ImageStitcher.Configuration.maximumDifference = 0.105` (identical to the iOS original).
- **Observed:** two independently-random-noise fixtures are correctly rejected, but a deliberately correlated pair (shared diagonal colour ramp, anti-correlated R/G) produced mean row difference ≈0.088 < 0.105 and was stitched (false positive). Real screenshots from the same app UI are exactly the intended match case, so this is inherent to pixel matching and not a port regression; recorded as a residual risk only.
- **Evidence:** characterized with a throwaway harness experiment; independent-noise rejection is locked in by `testUnrelatedImagesAreRejected`.

### D4 — Transparent source pixels always composite onto white (severity: nit / parity note)
- The macOS renderer fills the canvas with `CGColor(1,1,1,1)` (`ImageStitcher.swift:129`), while iOS uses the dynamic `UIColor.systemBackground` (dark in dark mode). Screenshots are normally opaque, so this is only visible for alpha inputs; white is a defensible choice for OCR-friendly exports. Verified by `testStitchesTransparentScreenshotsOntoOpaqueBackground`.

### Not defects (deliberate platform adaptations / improvements)
- Import: `PhotosPicker` → `fileImporter` + drag & drop + Finder/CLI open. Max 20 enforced with a visible warning; unreadable files are **skipped with a notice** instead of the iOS behaviour of clearing the whole selection with a generic error (a UX improvement, but a deliberate behavioural difference).
- Save: "Save to Photos" → `NSSavePanel` PNG export (required macOS equivalent, explicitly in scope).
- Share: `UIActivityViewController` → `ShareLink` on a temporary PNG (cleaned up on sheet dismissal).
- Preview: `fullScreenCover` → macOS sheet with two-axis scroll; preview downscaled to max edge 6000 while exports stay full-resolution (`ResultView.swift:169-181`).
- Stitching and import run off the main thread; both preserve ordering and use the same analysis/merge algorithm as the iOS original.
- Single-window policy via `Window` scene plus `CommandGroup(replacing: .newItem)` (no "New Window"); observed single main window in every launch.
- No `CFBundleDocumentTypes` is declared; `open -n -a <app> <files>` still delivered files through `application(_:open:)` in every observed launch (3/3 samples, 3/3 solid pairs), so the documented scripted flow works. Consequence: OpenStitch may not appear in Finder's "Open With" list for images — worth a future minor polish.
- Observation (not counted as a defect): launching the bundle executable directly (`.../Contents/MacOS/OpenStitch file1 file2`) from this non-interactive shell produced a running process with no window, twice; launching via `open` always worked. Most likely a session/activation artefact of the automation shell rather than an app bug — flagged for awareness because the `AppDelegate` command-line path exists for exactly that use.
